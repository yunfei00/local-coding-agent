# v0.3 Development Roadmap

Branch: `feature/v0.3`  
Stable baseline: `v0.2.0` / `main` at `9dd27dda72aa9d391e8b943e6ae3d464b2595559`

## Theme

**Extensible, repo-aware and task-isolated local coding agent.**

v0.2 completed the reliable single-Agent local coding loop. v0.3 focuses on extending that loop without turning the product into a full IDE or a distributed agent platform.

Primary goals:

1. MCP client support with the same safety model as built-in tools.
2. Better repository understanding without a vector database.
3. Explicit file/context selection through mentions and pinned context.
4. Stronger Git workflows and isolated task worktrees.
5. Persistent task plans/checkpoints for longer coding jobs.
6. Better observability of context/tool usage.
7. Preserve local-first behavior and the explicit commit/push rule.

## Guardrails

- `main` and `v0.2.0` remain the stable baseline until v0.3 is explicitly accepted.
- All v0.3 implementation lands on `feature/v0.3`.
- Every implementation phase must pass Windows + Ubuntu CI.
- Windows Setup + Portable remain release gates.
- Existing v0.2 tests stay green; new behavior receives regression coverage.
- Built-in permission modes remain authoritative: Read Only / Workspace / Full Access.
- MCP tools cannot bypass the local permission/approval system.
- Secrets must never be stored as plaintext in SQLite or exposed in diagnostics/logs.
- The Agent never creates a Git commit or pushes/publishes changes unless the user's current request explicitly asks for that action.
- Worktree creation/removal is explicit and visible to the user.
- v0.3 does not include full Multi-Agent orchestration, SSH Remote Workspace, browser/computer control, Plugin Marketplace, semantic vector indexing, or a full Monaco IDE.
- v0.3 should leave clean architectural seams for Multi-Agent + SSH in v0.4.

## Phase 22 — MCP client foundation

### Scope

- Add a provider-neutral MCP client layer in the Python Agent.
- Support:
  - local stdio MCP servers;
  - Streamable HTTP MCP servers.
- Implement server lifecycle:
  - connect;
  - initialize;
  - list tools;
  - list resources;
  - read resources;
  - disconnect/reconnect.
- Convert MCP tools into the existing Agent tool schema instead of creating a parallel Agent execution path.
- Namespace MCP tools to avoid collisions with built-in tools.
- Bound MCP response/output sizes and timeouts.
- Fail one MCP server independently without taking down the Agent.

### Acceptance

- Mock stdio and HTTP MCP servers work in tests.
- MCP tool discovery is deterministic.
- Built-in and MCP tools can coexist.
- Server disconnect/timeouts fail safely.
- Large MCP results are bounded before entering model context.
- Windows + Ubuntu CI pass.

## Phase 23 — MCP safety, settings and UI

### Scope

- Add `Settings -> MCP`.
- Configure servers with:
  - name;
  - transport;
  - command/args or HTTP URL;
  - enabled/disabled;
  - environment placeholders;
  - connection status.
- Store non-secret configuration in SQLite.
- Store credentials only through OS-protected/session/environment secret handling.
- Add trust metadata per server.
- Route MCP tool calls through the existing permission/approval path.
- Clearly label MCP tool cards with server + tool origin.
- Diagnostics reports server status but never credentials.

### Safety policy

- Read-only MCP tools may be allowed under Read Only only when declared and locally classified as read-only.
- Mutating/unknown MCP tools require Workspace/Full Access policy evaluation and approval as appropriate.
- Server declarations are not trusted blindly; unknown capability metadata defaults to the safer classification.
- MCP cannot silently perform Git commit/push through an external tool when the user did not explicitly request it.

### Acceptance

- MCP CRUD survives restart.
- Secrets never appear in SQLite/diagnostics.
- Disabled servers expose no tools.
- An untrusted write-like MCP tool cannot bypass approval.
- UI clearly distinguishes built-in tools from MCP tools.
- Windows + Ubuntu CI pass.

## Phase 24 — Repository Map + explicit context v1

### Scope

- Build a lightweight deterministic repository map without embeddings.
- Index:
  - directory structure;
  - project markers;
  - important configuration files;
  - symbols for common project languages;
  - test/build entry points.
- Initial symbol coverage:
  - Python;
  - JavaScript / TypeScript;
  - C / C++;
  - Java / Kotlin.
- Incrementally refresh changed files rather than re-scan the full repository every turn.
- Add explicit context controls:
  - `@file/path` mentions;
  - pin/unpin files;
  - pinned-context panel;
  - remove context item.
- Feed repository map + pinned files into the existing ContextBudgetManager with explicit token accounting.

### Acceptance

- Large fixture repositories produce a bounded repo map.
- Changed files refresh incrementally.
- Mentioned/pinned files are preserved ahead of ordinary history truncation.
- Missing/renamed pinned files degrade gracefully.
- Repository map does not include ignored binary/build trees by default.
- Windows + Ubuntu CI pass.

## Phase 25 — Git workflow v3 + task worktrees

### Scope

- Extend Git support with:
  - current branch;
  - branch list;
  - staged/unstaged summary;
  - stage;
  - unstage;
  - commit preparation;
  - explicit commit action;
  - worktree list/create/remove.
- Add worktree task isolation:
  - create a task worktree from the current branch;
  - open it as a separate project/session;
  - show source branch/worktree relationship;
  - remove safely when finished.
- Default worktree storage outside the source working tree to avoid clutter.
- Never auto-commit or auto-push.

### Safety

- Stage/unstage requires write permission.
- Commit always requires explicit current-user intent and approval.
- Push remains explicit-user-only and approval-gated.
- Worktree removal refuses dirty worktrees unless the user explicitly resolves/overrides the warning.

### Acceptance

- Stage/unstage/diff state is accurate.
- Worktree creation does not alter the original working tree.
- Dirty worktree removal is blocked safely.
- Commit cannot occur from an unrelated prompt or model initiative.
- Windows + Ubuntu CI pass.

## Phase 26 — Persistent task plans + checkpoints

### Scope

- Add structured Agent task planning for longer jobs.
- A plan contains:
  - goal;
  - ordered steps;
  - current step;
  - completed/skipped/blocked states;
  - verification criteria.
- Persist plans per Thread.
- Surface plan progress in the desktop without polluting chat text.
- Add checkpoints after meaningful milestones:
  - files changed;
  - commands/tests run;
  - current Git status;
  - unresolved blockers.
- Resume an interrupted/restarted task from persisted plan/checkpoint data.
- User can edit/reorder/mark plan steps before or between tool calls.

### Acceptance

- Short/simple tasks do not require a plan.
- Long tasks can survive app restart and resume.
- Plan state never claims a step completed without corresponding runtime evidence.
- Stop/cancel leaves a resumable checkpoint.
- Windows + Ubuntu CI pass.

## Phase 27 — Execution/context observability

### Scope

  - model/provider;
  - model steps;
  - tool calls;
  - tool duration;
  - context token estimate;
  - pinned/repo-map/history contribution;
  - retries/failures.
- Add source labels showing whether context came from:
  - system/rules;
  - pinned file;
  - repository map;
  - chat history;
  - tool output;
  - MCP resource.
- Improve Diagnostics with MCP/worktree/repo-map health.
- Add one-click copy of a sanitized turn trace for debugging.

### Acceptance

- Metrics remain bounded and do not grow unbounded in SQLite.
- Sanitized traces contain no API keys, MCP credentials or full secret values.
- Context-source accounting matches ContextBudgetManager decisions.
- Windows + Ubuntu CI pass.

## v0.3 Explicitly Deferred

These are intentionally deferred to v0.4 or later:

### Full Multi-Agent orchestration

Worktrees and persistent plans in v0.3 provide the foundation. Full parallel agents need scheduling, merge/conflict handling, GPU/provider concurrency policy, and a supervisor model before they are safe and useful.

### SSH Remote Workspace

Remote files/commands need a workspace abstraction that does not weaken the current local path/permission boundary. v0.3 MCP and worktree abstractions should land first.

### Browser / computer control

This introduces a much broader permission and privacy surface than shell/file tools and should not be mixed into the same release as MCP.

### Semantic vector index

v0.3 first proves whether deterministic repository maps, symbol indexing, search and explicit pinned context solve the majority of large-repository navigation. Vector indexing can be added later if measured retrieval gaps remain.

### Full Monaco IDE

The product remains an Agent workspace, not a general-purpose source editor.

## Suggested v0.4 direction
