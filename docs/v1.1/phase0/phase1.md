# v1.1 设计、里程碑与 Phase 1 执行指令

## 需求和架构

P0 目标是提高可验证交付率和任务连续性。沿用 `agent/server/main.py` 作为统一入口，`execution.py` 与 `runtime_events.py` 作为证据和恢复账本，`verification.py` 与 `workflow_delivery.py` 负责独立验证和交付。需求合同引用公开接口、保护文件、工作区范围、实际测试证据以及预期 Git 状态。旧任务缺少合同字段时继续读取原字段。合同应可从显式任务约束和项目规则生成，禁止把基准答案或 fixture 文件名放入生产规则。

P1 优化上下文：将确定的接口、最近失败、既有测试状态和已完成操作作为保留项，利用现有项目索引压缩工具输出。模型诊断标注能力来源、预算和 Provider 实际错误。中文需求的否定和兼容约束应作为独立回归。

| 阶段 | 范围 | 可独立验收 |
|---|---|---|
| Phase 1 | 交付合同和有限纠错 | 外部失败能归入明确证据类别；修复后重跑；无测试时保留未验证状态；旧 21 项与安全回归 |
| Phase 2 | 长任务和恢复 | 真取消、断线、从检查点恢复；完成操作无重放；环境错误能够有限收敛 |
| Phase 3 | 环境、上下文和中文体验 | 离线 uv/npm 复现，跨文件检索，中文约束和 Provider 实际诊断 |
| Phase 4 | 集成与稳定性 | 30 项加高风险三次复验、Windows/Ubuntu CI、发布回归，明确所有失败和阻断 |

回滚以独立提交和现有状态兼容为边界。关闭新增合同或恢复上一版本路径应保留 Checkpoint、权限与原任务。新增诊断必须脱敏，完整原始记录只留隔离环境。风险主要来自模型随机性、终端权限、不同机器的离线依赖、长上下文超时和任务恢复重放。关键真实测试出现安全问题时停止受影响场景。

## Phase 1 Codex 指令

从最新 main 创建独立 Phase 1 分支。读取 Phase 0 审计、用例和完整结果，对证据已确认的问题按失败签名复现。先做合同字段和最终验证证据的兼容设计，再实现跨 Python/Node/Git 的通用交付合同。明确区分语法成功、测试成功、功能验收成功和用户确认。发现测试失败时使用实际退出码和脱敏摘要提供一次有界纠错机会，保持原审批、取消和预算规则；重复签名无进展应保存 Checkpoint 并停止。禁止运行基准隐藏脚本作为生产工具、针对用例名称注入提示或修改其评分断言。单元及集成测试覆盖保护路径、验收失败、旧任务恢复和权限。运行受影响的真实 Gemma 用例、旧 21 项回归和双平台 CI。至少比较同配置的三次关键复验，记录每轮工作区、模型调用、验证证据和回滚方式。提交 PR 等待验收，发布与合并须遵循当前授权。
