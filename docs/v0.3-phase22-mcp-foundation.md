# v0.3 Phase 22 — MCP Client Foundation

## Scope

Phase 22 establishes the transport and tool-adapter foundation for MCP.

Supported transports:

- local stdio;
- Streamable HTTP.

The implementation uses the official MCP Python SDK v2 line, currently constrained to:

```text
mcp>=2.3,<2.4
```

## Architecture

```text
MCP Server
   |
   | stdio / Streamable HTTP
   v
MCPClientManager
   |
   +-- connect / disconnect / reconnect
   +-- tools/list
   +-- resources/list
   +-- resources/read
   +-- tools/call
   +-- per-server status/error isolation
   +-- timeout + response bounds
   |
   v
MCPToolAdapter
   |
   | BaseTool contract
   v
ToolRegistry
```

There is no separate MCP Agent Loop.

MCP tools are converted into the same `BaseTool` shape used by built-in tools.

## Tool namespace

MCP tools are namespaced to avoid collisions:

```text
mcp__<server>__<tool>
```

Example:

```text
mcp__filesystem__read_text_file
```

Names are normalized and bounded to the provider-safe tool-name length. Long names receive a deterministic hash suffix.

A collision after normalization is rejected instead of silently replacing another tool.

## Output bounds

MCP servers are external processes/services and must not be allowed to return unbounded model context.

Tool and resource payloads are serialized before entering the Local Coding Agent tool result.

Default maximum serialized payload:

```text
64,000 characters
```

When exceeded, the result becomes a bounded preview with:

- `truncated=true`;
- preview;
- original serialized character count.

This is independent of the later Context Budget compaction.

## Failure isolation

Each server keeps independent status.

A failed server:

- does not disconnect healthy servers;
- does not terminate the Agent;
- exposes a structured MCP client error;
- can be explicitly reconnected.

## Security boundary

Phase 22 intentionally does **not** make discovered MCP tools visible to the model through the runtime Permission Policy.

The current Permission Policy rejects unknown tool names, so MCP tools remain unavailable through normal Agent turns until Phase 23 adds explicit MCP trust/classification rules.

Phase 23 owns:

- Settings -> MCP configuration;
- persistence;
- secret handling;
- enabled/disabled state;
- read-only vs mutating classification;
- Permission / Approval routing;
- diagnostics status;
- model-visible MCP tool enablement.

This ordering is deliberate: transport capability lands before privilege.
