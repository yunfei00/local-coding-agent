日期：2026-10-22。开发分支：`feature/v0.3`。本轮实现与限制见 [实现说明](v0.3-implementation-notes.md)。最终执行结果见 [最终验收记录](v0.3-final-validation.md)。

## 自动化验证

在仓库根目录执行：

```powershell
uv sync --locked
uv run python -m unittest discover -s tests -p "test_*plan*.py" -v
uv run python -m unittest discover -s tests -p test_v03_runtime.py -v
```

运行时测试在 `manual-fixtures/phase26-task-plan` 的临时副本中使用实际读取、Patch、unittest 和 Git Diff。Provider 为确定性脚本，工具执行结果不作 Mock。

覆盖：计划按 Thread 隔离、SQLite 重启、自动建计划、同轮按序推进、真实工具证据、失败命令阻塞、禁止手写/伪造完成证据、只读权限、Stop 检查点、崩溃且没有检查点时的恢复确认、已成功修改的去重。

每次工具执行记录调用 ID、步骤 ID、状态、退出码和变更路径；不存储隐藏推理。恢复依据服务端数据，不仅依赖模型提示词。检查点保留真实 Git 状态、命令结果摘要和阻塞项；每个计划最多保留最近 50 份。

## 桌面人工复核

```powershell
.\manual-fixtures\phase26-task-plan\setup.ps1
.\scripts\dev\start.ps1
```

1. 只打开 setup.ps1 输出的临时工程。
2. 打开 Plan，创建“检查代码 → 修复加法 → 运行 unittest 并检查 Diff”的三步计划；新建 Thread 应不显示其他 Thread 的计划。
3. 编辑、排序 pending 步骤。普通短聊天不要求建计划；至少三个编号任务可自动建计划。
4. 开始执行并检查步骤下显示的实际工具状态。手动选择 completed 时，界面只提交该步骤已保存的成功工具 ID；没有成功工具时不能完成。
5. 失败测试必须显示失败并阻塞步骤。先修复失败或调整阻塞状态，不能把失败测试当作通过。
6. 执行中 Stop，关闭并重启，检查已完成步骤和未完成步骤仍在；点击 Resume info 查看检查点，检查工作区后再 Continue plan。
7. 即使通过协议直接发送恢复请求，未确认的中断步骤也不能执行；已成功的相同修改不会自动重放。
8. Read Only 下不允许文件写入；普通任务不 commit/push，显式 commit 仍需单独审批。

## 实际限制

自然语言 verification 目前要求成功命令证据，不能自动证明任意业务条件。计划若包含“运行测试以确认失败”，失败会如实阻塞，用户应检查结果后调整步骤，不能自动标记通过。

真实 1.5B 模型可能不能按计划发出结构化工具请求。确定性运行时测试验证程序行为，真实模型效果单独记录；人工视觉与实际使用复核仍是合并门禁。
